## 3. 答复结论

| 项 | 结论 | 关键说明 |
| --- | --- | --- |
| 1 删 80/443 安全组 | **同意** | 现状是「放行但无监听」，等于拆掉保险丝；Atlas 只用 8081 |
| 2 nginx 改绑回环 + Tailscale IP | **同意（有前提）** | Atlas 无 `0.0.0.0`/公网 IP 依赖；需保留 `127.0.0.1:8081`、`nginx -t` 失败即回退并记 incident |

## 4. 值得记下的判断

1. **`network_mode: host` 是第 2 项成立的前提。** 若 nginx 改回 bridge 网络，
   绑定 `100.65.110.80:8081` 会因容器内不存在该地址而 bind 失败，必须重评。
2. **第 2 + 第 4 项叠加会制造单点。** Tailscale 同时成为 SSH 唯一入口和 nginx bind 依赖；
   tailscaled 异常时 SSH 进不去、8081/8082 可能起不来。已在答复中要求确认
   阿里云控制台 VNC 可用，并记入 journal 作为应急入口。
3. **两项不必同一天上。** 任一项单独执行都不影响 Atlas，分开上可降低同时出问题的面。
4. **`atlas.conf` 的改动仍归 QuizGo 提交。** 源文件在 OpenQuizGo 仓库，
   `--with-nginx` 的 `rsync --delete` 会覆盖服务器上的手改（CONTRACT 2.1）。
5. **`status.sh` 的「待处理请求」列出全部 open 项，`inbox.sh` 才按 `to:` 过滤。**
   本次答复文件的 `to: quizgo` 不会阻塞 Atlas 的 `pnpm release`（已核对脚本源码）。

## 6. 第二轮：第 2 项撤回

对方用两条实测推翻了我对第 2 项的前提，撤回提议：

1. host 网络只保证「能 bind 宿主地址」，不保证「地址已存在」。
   我复跑：`100.65.110.80` → OK，`100.65.110.99` → `Errno 99`。我上一轮把前者外推成后者，结论过强。
2. `docker.service` 与 `tailscaled.service` 的 `After` 互不包含，重启后并发启动；
   绑定 Tailscale IP 会让 nginx 新增一个启动依赖，`restart: unless-stopped` 只能靠退避重试兜底。
3. 收益核算：8081/8082 安全组本就未放行，nginx 又有 `allow 127.0.0.1 + 100.64.0.0/10; deny all`，
   改绑只多藏一个「端口是否存在」。

**结论：撤回无异议，8081/8082 维持 `listen 8081;` / `listen 8082;` + allowlist。**

由此第 4 项的复合风险解除，可独立执行。

### 我补充的两点

- `restart: unless-stopped` 能自愈「tailscaled 起得慢」，真正致命的是 tailscaled 永久起不来
  或节点重新注册换 100.x 地址 —— 是尾部风险，撤回仍然正确。
- 既然暴露面完全交给安全组，就应可观测：建议 `status.sh` 加「公网自探」，
  期望 8081/8082 超时（exit 28），若变 `403`/`200` 即安全组被误开 → 报 drift。
- **纠正对方的闭环方法**：22 的规则按源限流（`→ 223.73.119.15/32`），从 ECS 自身发起本就是
  filtered（实测 exit 28），删前删后无差异；必须从 `/32` 那一侧发起或看控制台规则。

### 实测基线（2026-11-14 22:25，从 ECS 自身发起）

| 端口 | 结果 | 解读 |
| --- | --- | --- |
| 8081 / 8082 / 8080 | exit 28（timeout） | filtered，安全组未放行 |

这组数据同时独立印证了对方第 1 项的判断（80/443 确实放行）与「8081 安全组未开」的说法。
