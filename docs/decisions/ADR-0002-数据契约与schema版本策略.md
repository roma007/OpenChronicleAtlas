# ADR-0002：数据契约与 schema 版本策略

- **状态**：已接受（待用户最终确认）
- **日期**：2026-11-03
- **决策者**：项目负责人 + AI 开发助手
- **关联**：`docs/schema/atlas-schema-v1.0.0.md`

## 背景（Context）

平台的核心竞争力是「专题可插拔」：新增历史专题只需新增数据包，不改代码。这要求数据契约足够稳定、
可校验、可演进，并且要支持多语言与任意时间跨度。需求文档给出了 manifest / GeoJSON / 事件 JSON 的初版结构，
但缺少版本字段、多语言字段的统一约定，以及可选的扩展位。

## 选项（Options）

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| A. 直接使用需求初版结构，不设版本 | 上手最快 | 后续无法判断数据兼容性；破坏性变更会静默污染旧数据 |
| **B. 语义化版本 + zod 运行时校验 + 可选扩展字段** | 契约显式、错误可定位、可渐进演进 | 需要维护 schema 代码与文档同步 |
| C. 使用 JSON Schema 作为唯一事实源并生成 TS 类型 | 语言无关、工具生态好 | 生成链增加复杂度；zod 的运行时校验与错误信息更友好 |

## 决策（Decision）

1. 契约版本定为 **`1.0.0`**，写入 `manifest.schemaVersion`，必填。
2. 版本语义：
   - **PATCH**：文档澄清、注释、不影响解析的修正；
   - **MINOR**：只增不改（新增可选字段 / 新增枚举值），旧客户端可忽略未知字段；
   - **MAJOR**：破坏性变更，必须提供迁移脚本、更新 `docs/schema/` 并在 `docs/decisions/` 新增 ADR。
3. 采用 **zod** 作为运行时校验的事实源，TS 类型由 `z.infer` 导出，避免类型与校验两份定义。
4. 多语言统一为 `LocalizedString = string | { zh: string; en?: string }`；渲染时按 locale 回退到 `zh`。
5. 时间字段统一 `YYYY-MM-DD`（日粒度）或完整 ISO 8601；解析后转为 **UTC 日粒度 epoch 毫秒**。
6. 未知字段一律**保留但不报错**（zod `.passthrough()` 或宽松对象），便于 MINOR 演进；必填字段缺失则报错并指出路径。
7. 数据包路径全部相对 `manifest.json` 所在目录，禁止绝对 URL 之外的隐式约定；允许 `https://` 外链资源。
8. 每个专题必须提供 `sources`（史料来源）字段，允许为空数组但需在数据评审中说明。

## 后果（Consequences）

### 正面
- 平台与内容解耦，新增专题零代码。
- 校验错误可精确定位到字段路径，数据作者可自助排查。
- MINOR 演进不破坏旧客户端，符合三端不同发版节奏。

### 负面 / 代价
- 每次契约变更需同步：schema 代码、`docs/schema/`、CHANGELOG、三端升级。
- zod 校验大 GeoJSON 有性能开销，需要在加载阶段做一次并缓存结果。

### 后续行动
- M1 落地 `packages/shared/src/schema/atlas.ts` 与 `validateAtlas()`。
- 在 `data/atlases/long-march` 上跑通校验，并加一条 CI 脚本 `pnpm validate:data`。
- M5 接入第二专题时，验证契约无需改动即可复用；若需改动，按版本策略执行。
