# ADR-0003：双远程仓库同步策略

- **状态**：已接受（待用户最终确认）
- **日期**：2026-11-03
- **决策者**：项目负责人 + AI 开发助手
- **关联**：根 `README.md` §一

## 背景（Context）

需求要求所有代码与文档同时推送到 GitHub 与 Gitee，避免两端分叉。手工执行两次 push 容易遗漏，
尤其在提交频繁的里程碑阶段。

## 选项（Options）

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| A. 两个独立 remote（github / gitee），每次 push 两次 | 语义清晰，可分别重试 | 易漏推；需要记忆两条命令 |
| **B. 单 remote `origin` + 多个 `pushurl`** | `git push origin` 一次双推；fetch 仍只走 GitHub | 一端失败时整体返回非零，需要单独重试；`git remote -v` 会显示两行 push |
| C. CI 镜像同步（GitHub Actions 推 Gitee） | 本地零负担 | 依赖 CI 与密钥；Gitee 侧延迟；离线不可用 |

## 决策（Decision）

1. 采用 **方案 B**：`origin` fetch 指向 GitHub，`pushurl` 同时包含 GitHub 与 Gitee。
2. 首次克隆后的标准配置命令写入根 `README.md` 与 `docs/README.md`。
3. 每次推送后核对双端 HEAD 一致：

   ```bash
   git rev-parse HEAD
   git ls-remote origin refs/heads/main
   ```

4. 若其中一端推送失败（网络/权限），必须单独补推并记录在当轮对话档案的「提交与同步」表中。
5. 里程碑 tag 同样双推：`git push origin v0.1.0-m1`。
6. 密钥、证书、签名文件永不入库，`.gitignore` 已覆盖常见后缀。

## 后果（Consequences）

### 正面
- 一条命令完成双推，降低遗漏概率。
- 提交历史天然一致，避免 cherry-pick 对账。

### 负面 / 代价
- 单端失败时错误信息可能混在一起，需要用 `git push <url> <branch>` 单独重试。
- 新人若直接 `git clone` 后未配置 pushurl，仍可能只推到 GitHub，需要 README 提示与 Code Review 检查。

### 后续行动
- M1 首次推送时验证双端 commit 一致，并在对话档案回填结果。
- 可选：后续加 `scripts/verify-remotes.sh` 做一致性自检。
