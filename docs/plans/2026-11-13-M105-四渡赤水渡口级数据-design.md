## 1. 问题

四渡赤水不是四个单点，而是四次、多日、多渡口的渡河行动。当前数据把四次渡河压缩成三个县域点：

| 事件 | 原坐标 | 实际位置 | 偏差 |
| --- | --- | --- | --- |
| 土城战役 | 106.19, 28.33（习水县城） | 土城/青杠坡约 106.00, 28.27 | 约 20 km |
| 二渡赤水 | 105.81, 28.18（古蔺县城） | 太平渡约 106.04, 28.14 | 约 23 km |
| 三渡赤水 | 106.40, 27.79（仁怀市区） | 茅台渡口约 106.37, 27.86 | 约 8 km |
| 四渡赤水 | 105.81, 28.18（古蔺县城） | 太平渡约 106.04, 28.14 | 约 23 km |

因此地图上只能显示「县域示意」，不能回答「从哪个渡口过河」。

## 5. 数据结构与契约

不新增 schema 字段：

- 事件使用现有 `location`、`category`、`aliases`、`relatedIds`、`sources`；
- 渡口精度写入 `extensions.locationPrecision`（`ferry` / `approx`），旧客户端忽略；
- 路线精度沿用 `extensions.precision`（`campaign` / `schematic`）。

示例：

```json
{
  "id": "ferry-taipingdu-1935",
  "category": "渡口",
  "location": { "lng": 106.04, "lat": 28.141, "place": { "zh": "四川古蔺太平渡" } },
  "extensions": { "locationPrecision": "ferry" }
}
```

## 6. 技术取舍

| 选项 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 只改 4 个渡河事件坐标 | 改动最小 | 仍看不到具体渡口 | 不采用 |
| 为每个渡口建独立事件 | 可检索、可点击、可标注精度 | 同一区域事件增多 | 采用 |
| 只把渡口写进路线顶点 | 地图线条更细 | 无独立名称、无来源、不可检索 | 不采用 |
| 把渡口做成新 schema 图层 | 语义最纯 | 需要 UI/契约升级 | 本轮不做 |
| 把每个军团渡口写成确定结论 | 看起来最精确 | 史料互相矛盾 | 不采用 |

## 7. 兼容性、性能与安全

- 兼容性：事件与路线字段均为现有契约；新增 `extensions` 键旧客户端忽略；
- 性能：long-march 事件 80 → 90，路线 26 → 27，规模可忽略；
- 安全与隐私：无新增外部请求、无定位权限变化。

## 8. 测试策略

- `pnpm validate:data`：schema、ID、日期、引用完整性；
- `pnpm check:routes`：新增渡口事件与活动路线距离 ≤ 30 km；
- `pnpm build:search-index`：新增事件进入索引；
- `pnpm build:mobile-data --check`：移动端内置映射最新；
- `pnpm typecheck` / `pnpm lint`。
