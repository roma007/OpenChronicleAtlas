## 3. 每批标准流程（SOP）

1. 生成清单：

   ```bash
   pnpm check:heads --atlas <id> --json > /tmp/<id>-heads.json
   ```

2. 逐条读路线名、描述、事件、来源，按方案第 2 节判定 A—E；
3. 修数据：
   - 补连接线：新增路线或延长既有路线，写清名称、日期、描述、来源；
   - 补事件：新增点位事件，锚定端点；
   - 改坐标/拆段：按可靠点位修正，必要时标 `approx`；
4. 无法接线的独立起点/终点，写 `data/atlases/<id>/route-endpoints.allow.json`：

   ```json
   [
     {
       "entityId": "qing",
       "order": 41,
       "endpoint": "start",
       "reason": "1685 年雅克萨之战由瑷珲出兵，瑷珲为战役出发地，无前序路线",
       "source": "《清史稿》…"
     }
   ]
   ```

5. 校验：

   ```bash
   pnpm validate:data
   pnpm check:routes --atlas <id>
   pnpm check:heads --atlas <id>
   ```

6. 重新生成索引、写 docs 与 CHANGELOG、提交、发布；
7. 不改与端点无关的数据。

## 4. 判定优先级

1. 能补**连接线**的，优先补线（历史有行军/机动）；
2. 能补**事件**的，优先补事件（比 allowlist 有价值）；
3. 坐标明显错的，先改坐标；
4. 以上都不成立，才用 allowlist。

## 5. 验收标准

- [ ] `pnpm check:heads --all` 输出 0 个无来由端点；
- [ ] 每个 allowlist 条目都有 `reason`，并尽量有 `source`；
- [ ] 每条新增连接线都有名称、日期、描述、来源；
- [ ] 每批 `validate:data`、`check:routes`、`check:heads` 全绿；
- [ ] 所有改动按专题分批提交并发布；
- [ ] 文档与 CHANGELOG 同步。

## 6. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 为消线头虚构连接 | 新线必须有史料或明确「示意」说明；宁可 allowlist |
| 大批量改动难回滚 | 按专题分批，每批独立提交/发布 |
| 坐标修正引发事件偏移 | 每批全量跑 check:routes、check:heads |
| 其它专题史料不足 | 以现有来源为限，标 approx，不新造精确点位 |
| allowlist 变成垃圾桶 | 每条写 reason；B9 统一审计，能补线的移出 allowlist |

## 7. 工作量估算

- 小专题（三国、隋唐、宋元）：每批 0.5—1 小时；
- 明清：1—2 小时；
- 抗日三批：每批 2—4 小时；
- 全量复核：1 小时；
- 合计约 2—3 个工作日，分 8 次提交与发布。
